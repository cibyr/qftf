# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`qftf` ("QR code File TransFer") is a single-binary Rust CLI that sends a file p2p between two computers over [iroh](https://www.iroh.computer/). A third device (a phone running the companion web app, [qftf-web](https://github.com/cibyr/qftf-web/)) brokers the connection by scanning QR codes shown by each computer — no codes are typed by hand.

## Commands

- Build: `cargo build` (or `cargo build --release`)
- Run as receiver: `cargo run` (no args)
- Run as sender: `cargo run -- path/to/file`
- Lint: `cargo clippy`
- Format: `cargo fmt`
- Tests: `cargo test` (there are currently no tests)

FLTK needs system GUI/graphics libraries to build and run. The exact apt packages are listed under `[dist.dependencies.apt]` in `dist-workspace.toml` (cairo, fontconfig, GL, pango, X11/Xcursor/Xft, libpng).

Set `QFTF_URL_PREFIX` to point QR codes at a different web-app base URL (e.g. a local qftf-web dev server) instead of the default `https://cibyr.github.io/qftf-web/`.

## Architecture

Two source files:

- `src/lib.rs` — the wire/protocol contract shared with qftf-web. Just four constants: `ALPN` (iroh protocol id), `TX_PREFIX`/`RX_PREFIX` (URL-fragment tags the web app uses to tell sender QR codes from receiver QR codes), and `MAX_QR_BYTES`. **Changing any of these is a breaking protocol change that must be kept in sync with the qftf-web repo.**
- `src/main.rs` — everything else. `main` dispatches on argc: 0 args → `receive_file`, 1 arg → `send_file`.

### The three-party handshake

There is no direct sender↔receiver discovery; the phone web app wires them together:

1. **Sender** binds an iroh `Endpoint`, stats the file, generates a random 8-byte `token`, and serializes a `FileTransfer` struct (its `EndpointAddr`, file name, size, token) into the QR-code URL as `<prefix>#qftf-tx:<json>`.
2. **Receiver** binds an `Endpoint` and shows `<prefix>#qftf-rx:<EndpointAddr json>`.
3. The phone scans both QR codes, connects to the **receiver**, and pushes it the sender's `FileTransfer` JSON over a uni stream.
4. The receiver connects directly to the sender, opens a bi stream, and writes back the `token`. The sender verifies `token` matches before streaming the file. The token is the only authorization — it proves the connecting peer learned the details via the QR brokering.

### UI / async structure

The GUI is FLTK (`UI` struct in `main.rs`): a window showing the QR code as an SVG image, swapped for a text progress display once transfer starts. The app is `#[tokio::main]`; the network work runs in a `tokio::spawn`ed task that reports back to the FLTK event loop via an `app::channel::<Progress>()`. `UI::display_progress` drives `app.wait()` and drains progress messages; a `Progress { finished: true }` message ends the loop. `copy_with_progress` is a `tokio::io::copy` variant that fires a progress callback per chunk.

## Releases

Releases are built by [cargo-dist](https://axodotdev.github.io/cargo-dist) (`dist-workspace.toml`, `.github/workflows/release.yml`) and triggered by pushing a version git tag (e.g. `v0.2.0`). It produces shell/powershell/msi installers for macOS (arm64/x64), Linux x64 (gnu), and Windows x64. `.github/workflows/release.yml` and `wix/` are generated by cargo-dist — regenerate them with `dist` rather than hand-editing.
